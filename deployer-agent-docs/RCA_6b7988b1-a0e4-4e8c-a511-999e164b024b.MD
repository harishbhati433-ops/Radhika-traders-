# RCA — radhika-connect (radhikatraders.net) signup failing + Cloudflare 520 banner

## Problem statement
Intermittent Cloudflare red banner (520-type: "origin returned an invalid or incomplete response") on the signup page, and signup (`POST /api/auth/register` → Send OTP) failing. User suspected a production resource/tier limit (received an "85% resource usage" advisory email) and/or Resend email 429 rate-limiting.

## Verdict
**This is NOT a resource/tier problem and NOT a Resend 429.** The real cause is that **transactional/OTP email sends are failing with HTTP 402 "Insufficient credits"** on the Emergent email integration. Every email-dependent auth flow then returns **502**, which Cloudflare surfaces as the 520 banner.

## Evidence

### 1. Email credits exhausted — primary root cause (confirmed)
Backend logs (run 6b7988b1, active) show a continuous stream of, across the whole window:
```
email_service - ERROR - Email send error to <user>: HTTP 402:
{"error":"Insufficient credits","message":"Emergent credits are insufficient for this send.
 Add credits or check auto top-up under Universal Key in Buy Credits.","code":"insufficient_credits"}
httpx - INFO - HTTP Request: POST https://integrations.emergentagent.com/api/v1/email/send "HTTP/1.1 402 Payment Required"
```
Note: email is sent via the **Emergent email integration** (`integrations.emergentagent.com/api/v1/email/send`), not Resend directly. There is **no email 429/rate-limit** — the failure is **402 / out of credits**.

### 2. The 502s map 1:1 to the email-sending endpoints (confirmed)
All 502s are on flows that trigger an OTP email; non-email endpoints return 200 in the same window:
```
POST /api/auth/register            502 Bad Gateway   (Send OTP)
POST /api/auth/resend-otp          502 Bad Gateway
POST /api/auth/forgot-password     502 Bad Gateway
POST /api/security/reset-password/otp 502 Bad Gateway
POST /api/auth/login               200/401   (no email → fine)
GET  /api/auth/me, /api/wallet, /api/campaigns ... 200 OK
```
Status histogram for the signup window: 200×25, 202×3, **502×20**. The backend is turning the upstream email 402 into a 502 to the client → Cloudflare shows 520. (Some `register` calls return 200 — biometric-register path / cases that don't block on email.)

### 3. No resource exhaustion — tier upgrade is NOT required for this issue (confirmed)
- `get_tier`: tier_0 "Starter" — CPU 50m req / **250m limit**, memory 200Mi req / **512Mi limit**, replicas 2 (HPA/VPA disabled).
- `get_pod_events`: both pods **Running, Ready, restart_count = 0**. No `OOMKilled`, no exit 137, no `CrashLoopBackOff`, no eviction. `kill_findings` contains only a transient startup-probe 503 on a freshly created pod.
- The "85% resource usage" email is a capacity advisory and is **unrelated** to the signup 520s.

### 4. Secondary (minor) — transient 502/503 during pod rollovers (confirmed, not the main symptom)
A new pod (`...-cww9m`) was created 2026-11-04 10:37:58 (deployment scaled 2→1→2 over the window — node rescheduling, not a code deploy). During the few seconds before uvicorn binds :8001, nginx logs:
```
connect() failed (111: Connection refused) ... upstream: "http://127.0.0.1:8001/health"
Startup probe failed: HTTP probe failed with statuscode: 503
```
This produces a brief window of 502/503 (hence "intermittent") on every pod boot/rollover and during the several redeploys. It is normal rollout behavior, lasts seconds, and self-heals.

### 5. A few bad recipient addresses (minor)
Occasional `HTTP 422 "Undeliverable recipient"` (e.g. a typo'd `...@gimel.com`) — individual bad email addresses, not a systemic cause.

### Was a deploy in progress during the 520?
No. Latest run completed 2026-11-02 09:16 and is serving. The 10:37 pod creation on 11-04 was a scale/reschedule, not a deploy. Note: all recent runs (11-02, 10-27 "secret_reuse"; 10-21 redeploys) reuse the **same image sha256 d8a2ccad…** — worth confirming separately that the "global search / i18n / back arrow" build actually produced a new image, but it is unrelated to the 520.

## Current resource usage numbers
Live CPU/memory utilization is not exposable with available tooling. What is verifiable: tier_0 limits = **250m CPU / 512Mi memory**, 2 replicas; zero OOM/throttle kills; both pods Ready with 0 restarts. No evidence the origin is exceeding its tier.

## Fixes
1. **USER (primary):** Top up Emergent credits (Buy Credits / enable auto top-up under the Universal Key). This immediately restores OTP email delivery and clears the register/forgot-password/reset 502→520 failures.
2. **CODE (optional, hardening):** Signup/OTP endpoints currently bubble an email-provider failure up as a 502, which Cloudflare renders as the alarming 520 banner. Handle a failed email send gracefully — return a clear 4xx/JSON error (e.g. "OTP temporarily unavailable, retry") instead of 502 — so a provider hiccup never produces a Cloudflare 520.
3. **Tier:** No upgrade needed for this issue. The 85%-usage advisory is unrelated; revisit tier only if real OOM/CPU-throttle kills appear later.
